- 2026-08-28: Audited every outbound API request for savings and scored the rate-limit risk of a full fetch, in lockstep with the iOS session (the AEMET budget is per-key, so both platforms had to agree). Findings, grounded in the code: AEMET caps a key at 50 req/min, and its two-step model means each product is 2 HTTP GETs, both metered through `perform()` -> `RequestPacer.waitForSlot()`. A cold single-location refresh is ~13 GETs (~26% of budget), +4 per extra location; MITECO and Open-Meteo are separate hosts with their own budgets. The sliding-window `RequestPacer` (limit 45/60s, a process-wide singleton) makes the 50/min ceiling structurally un-trippable even in the worst realistic burst (a large forced multi-location refresh), and 429 exponential backoff already exists per call. Savings are already in place: coalesced refresh, the 1-hour per-location skip, the RSS-marker observation gate (zero keyed calls when nothing new), and per-area/comunidad/national dedup. Risk: LOW. Decision on the explicit question "should we put seconds between each API call?": NO — the limit is a rate not a spacing rule, so a fixed per-call delay would add ~13s of spinner to the common path for zero added safety; the savings lever is fewer calls (done) and the pressure valve is 429 backoff (present). If more margin is ever wanted, lower `RequestPacer.limit`, don't add delays. Also mapped a clean cross-process platform mirror vs iOS: Android runs app + widget + WorkManager in one process sharing one pacer (unifies the rate limiter, splits coalescing across two `WeatherRepository` instances -> volume dent only, rate bounded), where iOS splits the pacer across the app and widget-extension processes but unifies coalescing (-> a small cross-process rate dent). Both sides agreed to document, not build, the app-group shared-budget fix. No code changed; the write-up is the local `specs/api-request-audit.md`. Separately, verified the two iOS->Android localization parity catch-up items (widget config editor: N/A, Android's config is location-only and already localized; `HeroBackground.Family.displayName`: a hardcoded Spanish literal in `:core` but display-dead, the UI reads the localized `settings_hero_landscape/cityscape` pair) — both PASS, no change.

## Standing notes

- The AEMET key is shared and never committed (plan section 9). It is stored per-device via `SecretStore` (Keystore-backed `EncryptedSharedPreferences`), entered by the user, never in the binary or repo.
- `androidx.security:security-crypto` is deprecated by Google; we deliberately stay on 1.1.0-alpha06 (its terminal release, so "alpha" means "last", not "churning") because it is the documented, single-secret path and swapping in a plain Keystore-AES wrapper later touches only `SecretStore.kt`.
- The 24h/12h clock lives as a mutable flag on `:core`'s `AuraTime` (matching the Swift static), kept in step with the `Settings` DataStore boolean by `HoyViewModel` — the one place `:app` writes it. Compose reads it synchronously; `:core` stays android-free.
- Device location resolves to a `:core` `Coordinate`, which `SpainCities.nearest` turns into the closest bundled municipality (its INE then drives the forecast). `LocationProvider.current()` bounds the live-fix wait at 8 s (`withTimeoutOrNull`) before falling back to last-known and then `NoFix`, so a cold start can't hang the first paint. The three no-fix outcomes (permission denied, services off, no fix) are distinct all the way to the UI: "Hoy" shows a fallback banner, and Ubicaciones' "Usar mi ubicación" shows a matching notice.
- Location uses the platform AOSP `LocationManager` (via `LocationManagerCompat.getCurrentLocation`), never Google Play Services. This keeps Aura working on GMS-less devices and behaving the same on every OEM as on the emulator. `:app` acquires location and hands `:core` a plain `Coordinate`; `:core` stays free of any `android.*` or `com.google.*` import.
- Test-device plan: a Pixel is the clean development reference; the real OEM variety (Samsung, Xiaomi) comes from Samsung Remote Test Lab and Firebase Test Lab rather than more hardware. Watch for OEM background-killing (WorkManager for any refresh, never a bare service).
- The Home Screen widget (Jetpack Glance) never calls AEMET: it re-renders whatever the app last cached, reading the same `SnapshotCache` + `Settings` the app writes (no App Group needed on Android; the widget shares the app process). The app is the fetch hub and nudges `AuraGlanceWidget().updateAll()` after each refresh. Because Glance renders to RemoteViews rather than Compose, the widget cannot reuse `AuraSky`/`ConditionGlyph`; it bakes `Palette.skyGradientColors` into a bitmap and draws a restricted text layout. Each tile can pin its own place via `WidgetConfigActivity` (the `android:configure` picker), stored per-`GlanceId` in the tile's own Glance state under `PINNED_INE_KEY`; an unpinned tile follows the app's active location.
- Data-consistency contract, shared with iOS and reconciled 2026-08-28: there is ONE display-time resolver, `WeatherSnapshot.resolved(now)` (the analogue of iOS `resolved(at:)`), that re-anchors the timestamped hourly strip to the live clock via `upcomingHours(now)` and applies the most-recent-wins observation rule (`observedLeadsHero`/`observationIsFresh`/`observationDisplayTime`). Every surface calls it at its display boundary (the live clock for the app; `now` for the widget from cache) and then reads plain `current*` fields — no surface renders a metric from the raw fetch-time scalar, so one metric equals one value across every surface. UV keeps the daily clear-sky maximum ("Máx. hoy") strictly distinct from the live hourly value ("Ahora N"). The `:core` doc comments carry the "kept aligned with iOS" invariant; if the platforms ever change the resolution rule (e.g. strip-first-column, an `observedTemp` hero fallback, or a >24h honest-blank cap), change both together. Android has no Wear/complication/Lock Screen surfaces, so the surface class where iOS had to police this has no Android equivalent.
- The version stack is pinned deliberately. Read `CLAUDE.md` before bumping anything.
- Releases run through `/aura-android-release` (user-global skill, see Done 2026-08-30). It prepares everything and hands over a copy/paste block; the Play Console upload stays manual by design until a service-account + Gradle Play Publisher path exists.
- Play notifications gotcha (confirmed 2026-08-30): Play has no per-event "review approved" email like TestFlight. Rejections and account messages email reliably; an approval just flips the release status `In review → Available`. To catch the go-live, install the Google Play Console mobile app with push on, and/or watch the release dashboard; make sure the account contact/notification email is one I read so rejections arrive fast.
- MITECO's air-quality host has an incomplete TLS chain. The fix is a scoped Network Security Config trust-anchor for that domain only, not a global bypass (plan sections 5 and 10).
